# 图文采集与 LLM 加工交给独立的内容节点；BeeBox 只做语音，新增媒体直链

调用方要把小红书、知乎、X 这类以图文为主的信息流整理成素材。这些平台要抓页面、处理反爬和 cookie、读图上文字、生成摘要，都不是语音能力。决定：家里的系统分成三层：

- **home（网关）**：只负责编排，也就是一件事分几步、每步交给哪个节点、进度、重试、通知。它不解析页面、不调 LLM、不处理媒体。
- **BeeBox（语音节点）**：独占 GPU，提供转写，以后加 TTS。
- **内容节点**：独立的服务，同样运行在 Windows 主机上。它负责解析链接、采集图文、读图上文字，并负责全部摘要。

节点按资源类型划分（GPU 与本地语音模型 / 联网抓取与云端 LLM），不按平台或业务划分。两个节点都沿用 ADR-0009 的任务接口形式，所以 home 只需要一套调用代码。

BeeBox 这边的变化：

- 新增一种来源 **媒体直链**（`source.type = "direct"`）。yt-dlp 解析不了的平台（比如小红书），先由内容节点给出音视频文件地址，再交给 BeeBox 转写。BeeBox 里不写任何平台的页面解析代码。
- 媒体链接新增 X 和知乎 zvideo，两者都走 yt-dlp，不用 cookie。

**Considered Options**

- BeeBox 和 home 各写一套小红书解析器：两个仓库各维护一份反爬代码和 cookie，平台一改版两边都要修。
- BeeBox 新增“笔记抓取”能力：打破 ADR-0008 的语音边界；图片的保存也和 ADR-0011 的“媒体用完即删”冲突；GPU 主机还会变成爬虫机。
- 由 home 抓取并做 LLM 加工：home 会同时承担网关、爬虫和 LLM 三种角色，以后每加一个平台都要改 home。
- 内容节点只取原始内容，读图和摘要留在 home：home 仍然要做具体加工，网关的边界不清楚。**（被放弃：网关只编排，不加工）**
- yt-dlp 处理小红书视频：它不认 rednote.com 和短链，也解析不了页面数据里非空的 `new Set`。

**Consequences**

- ADR-0008 里“LLM 类文本加工由调用方负责”改为由内容节点负责。BeeBox 仍然不做 LLM。
- 媒体直链只接受 http(s)。地址解析出的 IP 是局域网、本机或保留地址时一律拒绝，跟随跳转后的每一跳都要检查。响应必须是音视频；文件大小上限沿用 `BEEBOX_MAX_UPLOAD_BYTES`。
- 直链可能过期。BeeBox 报可重试的下载错误；home 让内容节点重新解析一次，再重新提交。
- 混合内容（图文加视频）由 home 拆成两部分：视频交给 BeeBox 转写，图文交给内容节点采集，转写稿和图文一起作为摘要的输入。
- 以后加能力时，用 GPU 的放 BeeBox，需要联网或 LLM 的放内容节点。内容节点太臃肿时可以按 `kind` 再拆，home 改路由表即可。
