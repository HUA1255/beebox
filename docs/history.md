# 修复与决策历史

公开仓库只有一个初始提交。BeeBox 的开发在一个私有仓库里进行，前后共 70 个 issue、22 个 PR。本文从中挑出最能说明"怎么发现问题、怎么判断、怎么修、怎么验证"的案例，整理成可以直接阅读的记录。

代码注释和文档里出现的 `#47`、`refs #64` 这类编号，指的都是私有仓库的 issue，公开仓库里点不开。编号的含义见文末的[编号对照表](#编号对照表)。

---

## 1. 工作方式

每一项改动都走同一条流程。后面的案例里会反复看到这些环节：

1. **先写规格，再拆票。** 大改动先写一份 spec（例如 #29），写清问题、方案和用户故事，然后拆成可以独立完成的子票。每张子票都有一个"验收条件"清单，标明依赖和执行顺序。
2. **一票一分支一 PR。** PR 描述逐条勾选验收条件，写明测试数相对基线的变化（例如"632 passed，基线 629"）。如果实现偏离了原来的设想，要在 PR 里说明原因。
3. **审查后再合并。** 每个 PR 都经过一轮审查，审查意见分成"阻塞"和"不阻塞"两类。阻塞的修完再合；不阻塞的要么顺手修掉，要么开新 issue 跟踪。几个 PR 同时进行时，先用 `git merge-tree` 两两检查冲突，再定合并顺序。
4. **CI 必须通过。** 每个 PR 都在 `windows-latest` 上跑后端测试、控制台构建、控制台冒烟测试和部署脚本检查（见 [docs/ci.md](ci.md)）。
5. **真实环境验收。** 单元测试用假的语音引擎和假的视频平台，不占 GPU、不依赖网络。但每个阶段结束时，必须用真实模型、真实录音、真实平台跑一遍，不允许用假数据充当验收证据。下面好几个缺陷都是在这一步才暴露出来的。
6. **重要决定写成 ADR。** 选型和边界变化写进 [docs/adr/](adr/)。决定被推翻时，不删除原记录，而是追加后续或者标注"取代"。

开发主要和 AI 编程助手协作完成。规范入口是 [AGENTS.md](../AGENTS.md)，术语统一在 [GLOSSARY.md](../GLOSSARY.md)。

## 3. 方向调整

有两次大的方向调整，代码量的变化主要来自这里。完整的理由在 README 第 2 节"方案选型与理由"和对应的 ADR 里，这里只概括。

**从网页工作台到只留 `/v1` 接口（#29，[ADR-0008](adr/0008-beebox-voice-service.md)、[ADR-0009](adr/0009-unified-job-api.md)）**

上游 asrbox 是一个完整的工作台，有字幕编辑、AI 校对、翻译、聊天、MCP、桌面打包等功能。但唯一的重度调用方 home 一样都不用，这些代码反而拖慢改动、误导参与开发的 AI 助手。所以整体删除，只留一套统一的任务接口（文件和视频链接共用一种 Job 资源）。控制台降级为"另一个调用方"，只能使用公开接口，不留后门。

**从 Docker 两容器到 Windows 原生服务（[ADR-0010](adr/0010-windows-native-deployment.md)）**

Gate 2 按 docker-compose 两容器交付并通过了验收。但实际运行的机器是 Windows，GPU 容器要经过 WSL，api 镜像有 23.7 GB，线上实际跑的又是另一套计划任务加脚本，与 main 脱节。最后改为 uv 锁定依赖、WinSW 托管服务、按 git tag 部署。

## 4. 案例

### 4.1 转写稿按 84 个字硬切（#16–#23）

**现象**：82.7 分钟验收录音的转写稿里，相邻两段常常正好各 84 个字，断点落在句子甚至词的中间，例如"我们应该去做一些｜什么样的事情"。

**根因**：84 来自上游的字幕排版预算（每行 42 字 × 2 行）。上层的配置项没有传下来，所以这个值始终是 84。分组逻辑只判断"累计字数是否达到上限"，标点完全不参与。而 Qwen3 路径先整段解码再做强制对齐，每个字都有真实的起止时间，按句子切分几乎没有额外成本。

**决定**：
- 分段改成句子级，84 字预算移出转写管线，只留在导出时的换行处理里。
- **只切不改**：所有分段按顺序拼回去，必须和原始识别文本逐字一致。这条写成断言。
- 段落由句子分组得到：软下限 10 秒、硬上限 120 秒；一个段落只属于一个说话人，短段只和同一说话人合并。

**验收与迭代**：在真实录音上跑完整管线，做改造前后对比。第一轮"恰好 84 字的分段"从 240 段降到 0，跨说话人段落为 0，逐字回拼一致。但人工抽查时发现，只有 46.2% 的段落以句末标点结尾，有的段落在"麻烦举个｜手。"这种地方断开。于是增加一条规则：按停顿切分时，切点之前必须已经出现句末标点。第二轮这个比例升到 **95.5%**，前 10 分钟从 11 段合并成 4 段，观感达标后才关单。

**体会**：指标全部达标不等于结果好用，最后一轮要靠人工抽查来定。

### 4.2 一个撇号让长录音转写失败（PR #27）

**现象**：一段 99.5 分钟的录音在第 3 块（共 51 块）失败：`aligner tokens (566) do not match non-punctuation text (563)`。

**根因**：识别文本里有 3 处 `Honey's`。撇号算标点，不参与计时，所以文本的非标点字符是 563 个。但对齐器把 `Honey's` 当作一个 token，原代码按原始字符数（7）计入，3 处正好多出 3 个，长度校验必然失败。

**修复**：token 长度只统计参与计时的字符。撇号仍然作为不计时字符贴回前一个字，逐字回拼不受影响。如果是真正的长度不一致，仍然报错，不放过。

**验证**：用失败录音中那一块真实的 120 秒音频复现，修复前 566 对 563，修复后正常产出 15 段。新增 4 个回归测试：词内撇号、token 内空格、逐字回拼，以及"真实不一致仍然拒绝"。

### 4.3 上线前回头补审，发现 6 处偏差（#64–#69）

BeeBox 改造的主 PR（#58）合并后、正式上线前，对照规格把合并结果逐条补审了一遍，发现 6 处实现与规格不一致。每处单独开票、单独修复、单独审查（PR #70–#75）。几个 PR 同时进行，先用 `git merge-tree` 两两检查，只有一对 PR 有一处小冲突，据此定下合并顺序。

| 票 | 问题 | 修法 |
| --- | --- | --- |
| #64 | 部署时先暂停队列再重启服务，但服务启动时把排队中的任务也当作"被中断"，判为失败 | 只中断真正在跑的任务；排队中的任务按原提交顺序重新入队；被中断任务保留中断时的进度，不再显示 100% |
| #65 | B 站 AI 字幕轨道名形如 `ai-zh`，语言被识别成 `ai`，中文 AI 字幕选不上，AI 翻译出来的 `ai-en` 反而可能被选中 | 在纯选择层统一规范化：`ai-<lang>` 按 `<lang>` 识别；与视频原语言不同的轨道视为平台机翻，永不选用 |
| #66 | 规格要求 B 站登录不可用时直接失败，但"从未登录"时会悄悄降级成匿名 ASR | 登录状态为"未登录"或"已失效"时，在任何网络请求之前就报 `VIDEO_LOGIN_REQUIRED`；平台判断改用解析后的链接，不再做 URL 子串匹配 |
| #67 | yt-dlp 结束时会把 cookie 写回传入的文件，每个任务都会改写凭证，还可能和每日刷新同时写 | 每次下载会话使用凭证的临时副本，结束时删除（成功、失败、取消都覆盖）；真实凭证只由登录和刷新流程写入 |
| #68 | 扫码改走 TV 通道后，刷新令牌被交给 Web 端的刷新接口，两者是否匹配从未验证 | 见下文 |
| #69 | 免鉴权的健康检查暴露了当前任务 id；不支持的链接先创建任务再置为失败 | 不带 token 时只返回概要信息；无效链接在写任何数据之前直接返回 400 |

其中几个值得展开：

**#64 审查时又多发现一层。** 第一版修复把排队任务逐个重新提交。审查指出：只要有一行数据损坏，提交抛出异常，服务就起不来，WinSW 会反复重启它。于是改成每个任务单独捕获异常：失败的那一行标为可重试的 `TASK_RESUME_FAILED`，其余任务照常恢复，并补了"一行坏数据不影响启动和其他任务"的测试。

**#67 测试设计得比较狠。** 测试用一个假的 YoutubeDL，在读元数据、下载、退出三个时机都往 cookie 文件里写垃圾内容，然后断言：真实凭证的字节和修改时间都没变；会话看到的是另一个临时副本；会话结束后副本已删除；日志里既没有临时路径也没有 cookie 值。同时验证了下载进行中触发一次刷新，两边互不覆盖。

**#68 选择"不做"。** 查证后发现：TV 扫码拿到的刷新令牌属于 app 端，而锁定版本的 `bilibili-api-python` 只实现了 Web 端的 cookie 刷新，两者不匹配；这个库已经归档，不会再有 TV 续期的实现。如果自己实现未公开的签名流程，风险和维护成本都不可控。所以采用票里允许的另一条路：**每天只做失效检测；失效时健康检查报 `expired`，由调用方提醒我重新扫码**。ADR-0012 随之改写，并写明代价：最长约 180 天需要重新扫码一次。

这张票还有一项验收需要用真实账号完成，所以 PR 写的是 `refs #68` 而不是 `Closes #68`，避免合并时自动关单。之后在开发实例上用真实账号扫码，手动触发一次检查，确认状态仍然有效、cookie 文件的哈希和修改时间完全不变，把记录（不含任何 cookie 值）贴回 issue 才关闭。

**体会**：PR 合并不代表符合规格。上线前对照规格回头再审一次，用很小的成本挡住了 6 个会在线上出问题的偏差。

### 4.4 假平台测试全部通过，真实 B 站却不行（#56）

**现象**：删除旧接口后，按规格在 Windows 开发实例上走 4 个真实场景：长录音、有字幕的 B 站视频、无字幕视频、YouTube 视频。其他 3 个通过，但"有字幕的 B 站视频"任务虽然成功了，走的却是 GPU 上的语音识别，而不是平台字幕。

**排查**：匿名状态下，B 站接口返回的字幕列表是空的。试了 260 多个公开视频都一样，说明 B 站已经把 CC 字幕放到登录之后了。登录后又连续暴露出 3 个真实缺陷：

1. `bilibili-api` 的 Web 扫码流程现在不返回 `SESSDATA` 等关键 cookie，改用 TV 扫码通道才能拿到完整 cookie。
2. yt-dlp 只有在 `writesubtitles` 打开时才会填充字幕信息。之前没开，所有 B 站视频都被当成"无字幕"。
3. B 站字幕是内联数据，没有下载链接，适配器需要支持直接读取内联内容。

修完后，同类视频 3 秒完成，全程不进 GPU 队列。

**体会**：假平台只能证明"我的逻辑符合我对平台的理解"，证明不了理解本身是对的。真实验收不能省。

### 4.5 上线当天的连锁问题（#85 → #88 → #91）

1.0.0 上线后，提交一个**没有字幕**的 B 站视频，任务失败，错误码是 `DOWNLOAD_NETWORK_ERROR`，可重试。上线前测的视频都有平台字幕，不会下载音轨，所以这条路径没被覆盖到。

**第一层（#85）：yt-dlp 找不到 ffmpeg，而且报错归类错了。** BeeBox 自己能在固定工具目录找到 ffmpeg，但没有把路径告诉 yt-dlp，yt-dlp 只会去 `PATH` 里找。另外这个错误被归成"网络错误、可重试"，实际上跟网络无关，重试多少次都一样失败。修复如下：
- 把 ffmpeg 路径传给 yt-dlp。票里原本建议传"所在目录"，但我读了锁定版本 yt-dlp 的源码，发现传目录时它会拼出不带扩展名的 `<dir>\ffmpeg`，在 Windows 上找不到；传可执行文件路径才会自动派生同目录的 `ffprobe.exe`。所以实现偏离了票面建议，并在 issue 里写明了原因。
- 新增错误码 `LOCAL_TOOL_MISSING`，标为不可重试，提示里说明去哪里配置工具路径。

**第二层：真机验证时又发现一个问题。** 下载音轨的会话继承了"写字幕"选项，B 站会把弹幕 XML 写进同一个临时目录。原代码取"第一个剩余文件"作为音频，拿到的是 XML。改为下载音轨时关闭字幕输出，并显式选择 `.wav` 文件。

**第三层（#88）：开发实例在普通终端里起不来。** 启动脚本探查受权限保护的线上配置文件时，`Test-Path` 抛出"拒绝访问"，而脚本设置了 `$ErrorActionPreference = 'Stop'`，于是直接中止，而不是按设计"读不到就警告"。如果改用管理员终端，管理员权限又会让"模型目录只读"的检查失败。新增一个安静的路径探针（读不到返回 false），先解除阻塞。管理员终端下误报的部分记为 #78，后续处理。

**第四层（#91）：部署 1.0.1 时脚本中断，线上服务被停掉。** PowerShell 5.1 在 `Stop` 模式下，会把原生命令写到 stderr 的普通进度信息（比如 git 的 `From https://...`、uv 的 `Checked 180 packages`）当成终止错误，即使命令的退出码是 0。第二次中断时服务已经停了，只能手动恢复。修复方法是：执行原生命令期间临时切换错误处理模式，stderr 写到临时文件再读回；判断成功与否只看退出码。之后用真实部署验证，完整走完同步依赖、迁移、记录 commit、启动服务、健康检查、恢复队列的流程。

最终，同一个无字幕视频在开发实例和线上都跑通，结果一致（544.9 秒音频转出约 9,900 字）。

**体会**：
- 错误分类本身也是功能。错把"本机缺工具"报成"网络错误、可重试"，会把排查方向和自动重试一起带偏。
- 每修一层都要在真机上验证一次，这次连续挖出了四层问题。
- 部署脚本也要按生产代码的标准对待，它一出错，停掉的是线上服务。

### 4.6 审查中的小判断

几次审查里不大但有代表性的判断：

- **错误提示要对得上平台**（PR #70）：`VIDEO_LOGIN_REQUIRED` 的提示原本只写"请到 B 站扫码登录"，但 YouTube 年龄限制视频也报这个错误码。改成区分两个平台各自的处理方式。
- **中文语言族要等价**（PR #73）：原语言为 `cmn` 时，`ai-zh` 会被误判成机翻。改为 `zh` 和 `cmn` 视为同一语言族，并补上测试。
- **故意不吞掉清理失败**（PR #72）：临时目录清理失败时，选择让错误暴露出来，不启用 `ignore_cleanup_errors`，以免泄漏被悄悄掩盖。
- **区分偶发失败和回归**（PR #75）：CI 第一次失败在一个和改动无关的时序用例上（模型在取消之前就下载完了）。本地连续通过 3 次后，只重跑失败的 job，并在 PR 里记录原因，没有为了让 CI 变绿去改测试。
